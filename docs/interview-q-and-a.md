## 1. 60 秒项目介绍

**面试官：请简单介绍这个项目。**

**候选人：**

智营台是一个面向国内多店铺货架电商的本地运营与物流协同平台。运营流程从经营数据中识别异常商品开始，运营选品后，由商品优化 Agent 生成标题、卖点、详情、关键词和属性建议，再由独立合规 Agent 做语义审核，同时服务端执行确定性规则检查。审核不通过最多自动修订两次，之后进入人工修订；只有复核通过的当前版本才能提交主管审批，批准后在 PostgreSQL 内完成本地发布并创建独立的平台投递任务。物流工作台则管理运单轨迹、时效、退货和异常工单。

技术上我用 Vue 3、FastAPI 和 PostgreSQL 做模块化单体，用 PostgreSQL 租约表加 `SKIP LOCKED` 实现可恢复 Worker 队列，用 LangGraph 和 PostgreSQL Checkpointer 保存运营流程位置。RAG 使用本地 BGE-M3、Milvus dense/sparse 混合召回、RRF 融合和 Reranker。模型输出不直接成为业务事实，而是经过 Pydantic Schema、事实 allowlist、引用版本校验、双轨合规、人工审批、版本锁和幂等事务。部门、角色和店铺范围同时约束页面、API 与后台写入。

当前运营、物流、知识、评测、审计和系统管理前端均已有源码和验证。真实边界是：平台投递只连接仓库内 `contract_simulator`，物流轨迹来自人工录入或演示数据，规则巡检 Agent 不调用大模型，也没有真实电商平台或承运商集成。

**面试官判断点：** 候选人是否能在一分钟内同时说清业务闭环、技术难点和真实边界。

## 2. 业务理解

### Q1：这个项目解决的核心业务问题是什么？

**候选人：**

不是简单“用 AI 写文案”，而是解决运营决策与执行之间的断链：先判断哪些商品值得处理，再生成有事实依据的方案，然后完成合规、人工修改、主管审批和可追溯发布。业务价值在于缩短人工筛选与改稿时间，同时降低模型编造、违规文案和未经授权发布的风险。

**面试官追问：** 如果只做文案生成页面，会缺什么？

**回答要点：** 缺可信诊断、规则引用、版本控制、责任分工、审批、恢复和审计，无法形成可在企业中使用的闭环。

### Q2：为什么运营首页设计成任务工作台，而不是经营大屏？

**候选人：**

系统的主要用户是运营和主管，他们最常见的问题是“现在有什么要处理”，而不是“再看一组图表”。工作台按待处理、运行中、异常和最近完成组织任务，更直接支持分析、选品、修订和审批。指标仍在任务详情中展示，但不抢占首页主路径。

**面试官判断点：** 是否从用户任务出发，而不是为了展示技术堆页面。

### Q3：为什么经营分析不能完全交给大模型？

**候选人：**

曝光、点击、转化、退款和库存是可计算事实，交给模型既贵又不可复现。项目先由 SQL 和确定性代码计算指标与异常集合，模型只解释影响、排序和建议。模型返回后，服务端再按 product_id 重附加可信指标和证据，因此模型无法伪造销售额、库存或不存在的商品。

### Q4：目前如何识别问题商品？

**候选人：**

演示版覆盖低转化、销售下滑、高退款和库存风险。比如低转化要求点击至少 50 且转化率低于店铺中位数的 60%；销售下滑比较前后等长周期；高退款要求销量至少 10 且退款率达到 10%；库存风险比较当前库存与近七天销量。规则可复现，但不是生产阈值，正式上线应由历史数据、类目和业务成本校准。

**面试官追问：** 为什么不现在就做机器学习异常检测？

**回答要点：** 当前没有真实标签和线上反馈，规则足以验证流程；先建立可解释基线，有可靠历史数据后再评估季节性模型或监督学习。

### Q5：为什么只让运营选一个候选商品继续？

**候选人：**

这是业务级 Human-in-the-Loop。分析可以一次给出多个候选，但优化和审批涉及业务责任、模型成本和商品版本冲突。由运营确认优先级后再创建独立优化流程，边界清晰，也避免一个长期图一直等待人工选择。

### Q6：为什么不能让 AI 自动发布？

**候选人：**

发布会产生真实业务责任。模型可能受到错误数据、过期规则或语义误判影响，所以系统把“建议权”和“发布权”分开：AI 生成和审核，人负责选品、人工修改和主管审批。审批通过后，系统原子更新本地商品快照并创建平台投递任务；投递 Worker 当前只调用本地契约模拟器，不能表述为已发布到真实店铺。

### Q7：为什么价格和 SKU 只提供建议但不应用？

**候选人：**

价格和 SKU 影响订单、库存和财务，通常需要更严格的角色、审批和平台同步。本阶段没有价格专员和价格审批模型，直接应用会扩大业务风险。因此它们只读展示，人工修订也不能篡改，模拟发布只更新标题、卖点、详情、关键词和属性。

### Q8：如何处理 AI 的误报和漏报？

**候选人：**

异常集合由确定性规则产生，运营可以不选择误报候选；模型解释有置信度和可追溯证据。漏报需要通过离线标注集、运营反馈和后续真实数据评估 Precision@K、Recall 和不同类目阈值。当前项目只能证明机制，不能证明真实业务泛化效果。

### Q9：如何衡量项目的业务收益？

**候选人：**

当前没有真实平台数据，所以不声称提升 GMV。上线验证应分两层：流程指标包括候选采纳率、草稿提交率、主管通过率、平均修订次数、处理时长和违规拦截率；业务指标通过 A/B 实验观察点击率、转化率、退款率和毛利变化，同时控制类目、流量和季节因素。

### Q10：知识库在业务上解决什么问题？

**候选人：**

它把平台规则、类目规范和企业文案规范变成有版本的可引用依据。运营不只看到“AI 说不可以”，还可以看到具体文档、版本和 chunk。更新规则后，旧版本会停用，后续方案只使用当前 active version，便于复核和审计。

## 3. 架构与工程取舍

### Q11：为什么选择模块化单体，而不是微服务？

**候选人：**

目标是单机 Docker Compose 演示，没有跨团队部署和独立扩缩容需求。模块化单体已经能分离 API、领域服务、Worker 和外部依赖边界，同时保持事务简单。微服务会引入网络失败、分布式事务、服务发现和部署成本，但没有对应业务收益。

**面试官判断点：** 是否会根据规模选择架构，而不是把微服务当高级答案。

### Q12：为什么不用 Celery、Redis 或 Kafka？

**候选人：**

项目已经需要 PostgreSQL 保存业务事实。用任务表、行锁和租约就能满足本地持久任务、并发领取和重启恢复，少维护一个基础设施。若未来出现高吞吐、复杂调度、海量事件扇出或独立消费者，再引入专门消息系统。

### Q13：`FOR UPDATE SKIP LOCKED` 如何防止重复领取？

**候选人：**

Worker 在事务中查找 `accepted` 或租约过期的任务，并对候选行加锁。`SKIP LOCKED` 让其他 Worker 跳过已锁行，领取者同时写入 owner、过期时间、processing 状态和尝试次数。这样同一时刻只有一个 Worker 获得该行。

**面试官追问：** Worker 领取后立刻宕机怎么办？

**回答要点：** 租约到期后可被新 owner 重领；每个外部调用和写入边界前续租，所有最终写入校验 owner 和未过期租约。

### Q14：项目能保证 exactly-once 吗？

**候选人：**

不能承诺跨数据库和外部 HTTP 的绝对 exactly-once。项目实现的是至少一次执行、租约互斥和幂等副作用：允许节点重放，但候选、Agent 调用、revision、review、审批和发布都有唯一键或请求哈希，旧 owner 也不能提交结果。

**面试官判断点：** 是否理解 exactly-once 通常是业务语义，而不是一句中间件配置。

### Q15：为什么既有 `workflow_runs`，又有 LangGraph checkpoint？

**候选人：**

职责不同。`workflow_runs` 是面向业务和 API 的事实源，保存类型、生命周期、质量、owner、租约和安全输出；checkpoint 保存图执行到了哪个节点。恢复时 checkpoint 提供位置，但业务状态仍从 PostgreSQL 重新加载和校验，避免把可能过期的图状态当成真相。

### Q16：LangGraph 在这里的实际价值是什么？

**候选人：**

分析图是顺序节点，优化图包含“生成 revision—合规审核—通过/再修订/转人工”的条件循环，人工复核又是独立图。LangGraph 让节点、条件边、thread_id 和 checkpoint 统一表达，并能在进程重启后恢复。若流程只有两三个同步步骤，普通函数就够了；这里主要价值是持久恢复和受限循环。

### Q17：为什么把分析、优化和人工复核拆成不同 workflow type？

**候选人：**

它们的生命周期和人工边界不同。分析在 `awaiting_selection` 停止；选品后创建优化任务；人工修订创建新的 manual_review 任务。拆开后每种 Worker 只领取自己的类型，状态约束更清晰，也避免一个图长时间跨越多个业务动作。

### Q18：如何防止旧 Worker 覆盖新 Worker 的结果？

**候选人：**

所有续租、步骤更新和终态写入都带 `workflow_type + processing + lease_owner + lease_expires_at > now()` 条件。外部 RAG 或 DeepSeek 请求前也先续租。旧 owner 即使稍后恢复，也无法更新任务或写入新副作用。

### Q19：为什么 Worker 的尝试上限是 3？

**候选人：**

它是演示环境的有限失败预算，防止永久坏任务不断占用队列。具体生产值应结合错误类型、处理成本和告警策略决定。外部调用的 HTTP 重试和任务重领是两个不同层次，不能把两者混成无限重试。

### Q20：当前架构最先遇到的扩展瓶颈是什么？

**候选人：**

经营分析对每个商品逐个聚合查询，在 300 商品演示规模可接受，但大店铺会出现 N+1 式查询成本。生产化优先改成批量 SQL 聚合、预计算日指标或数仓层，而不是先拆微服务。其次是本地 BGE/Reranker 的 CPU/GPU吞吐，需要批处理、模型服务化或缓存。

## 4. Agent 与模型可靠性

### Q21：为什么称为多 Agent，而不是一个大 Prompt？

**候选人：**

三个 LLM 角色的目标和权限不同：经营分析 Agent 解释确定性指标，优化 Agent 生成商品方案，合规 Agent 独立找风险且不能直接改稿。把职责拆开可以分别定义 Schema、Prompt 和评测，也避免生成者自己批准自己的输出。物流模块另有一个“规则巡检 Agent”，但它只是有证据的确定性规则程序，不调用 LLM。流程仍由同一平台编排，并不意味着每个 Agent 都是独立微服务。

### Q22：如何防止模型编造商品事实？

**候选人：**

有四层控制：服务端构造可信输入；Prompt 提供允许的 fact path 和 rule chunk ID；Pydantic 禁止额外字段；确定性校验逐项验证 current value、目标 SKU、价格、属性来源和 evidence。只有通过的字段才会进入 revision，模型不能凭自然语言绕过这些边界。

### Q23：结构化输出失败怎么办？

**候选人：**

先用 Pydantic 解析和业务校验。若响应存在但 Schema 不合法，可以发起一次独立 schema repair；仍失败则根据流程降级或转人工，不递归修复。每次逻辑调用和传输尝试都有独立审计记录。

### Q24：为什么不保存模型完整原始响应？

**候选人：**

完整 Prompt 和响应可能含商品正文、内部规则或敏感信息，而且大多数排障只需要输入哈希、模型、Prompt 版本、错误码、Token 和耗时。项目优先最小化存储。若生产需要回放，应建立受控、脱敏、分权限且有保留周期的日志系统，而不是直接写普通业务表。

### Q25：LLM 出现 timeout、429 或 5xx 怎么处理？

**候选人：**

统一运行时只对 timeout、transport、429 和 5xx 做有限重试，最多三次 HTTP 尝试。缺 Key、401、403 和非临时 4xx 不重试。经营分析只要确定性事实成功，就可以输出固定中文降级结果；商品优化或合规依赖不足时进入 `pending_manual/degraded`，不能伪装成正常通过。

### Q26：为什么质量状态和生命周期状态要分开？

**候选人：**

生命周期回答“任务进行到哪里”，质量回答“结果有多可信”。例如经营分析可以已经到 `awaiting_selection`，但模型解释降级；如果只用一个状态，就会把可用但不完整的结果和失败任务混在一起。项目使用 `normal / partial / degraded` 独立表达质量。

### Q27：自动修订为什么最多两次？

**候选人：**

无界 Agent 循环会放大成本、延迟和错误，而且模型可能一直在同一问题上振荡。系统允许初稿后最多两次自动修订，revision 的 iteration 固定为 0、1、2。仍不通过就进入人工处理，这个上限同时由工作流路由、数据库约束和测试守住。

### Q28：优化 Agent 和合规 Agent 会不会互相污染？

**候选人：**

合规 Agent 不修改内容，只输出结构化 violation 和 required change。下一轮优化 Agent 接收的是受验证的修改要求，而不是合规模型的任意自由文本。确定性和语义 violation code 还有固定闭集，引用 ID 也必须属于当前 allowlist。

## 5. RAG

### Q29：为什么选择 BGE-M3？

**候选人：**

项目需要中文规则检索，并希望同一模型提供 dense 语义向量和 sparse 词项权重。BGE-M3 能覆盖这两条召回路径，适合中文、规则术语和关键词混合场景。选择它是项目约束下的工程取舍，不代表对所有数据集最优。

### Q30：为什么要 dense、sparse 和 Reranker 三层？

**候选人：**

dense 擅长语义近似，sparse 擅长禁限词、型号和规则术语等精确匹配。两路结果用 RRF 按排名融合，避免直接比较不同分数空间；Reranker 再对少量候选做更精细的 query-document 相关性判断。离线评测同时比较 dense、sparse、hybrid 和 hybrid_rerank。

### Q31：为什么 Milvus 不是知识事实源？

**候选人：**

向量索引可能延迟更新或残留旧版本。PostgreSQL 保存文档当前版本、激活状态、规范正文和元数据；Milvus 只返回候选 chunk ID。最终引用必须回 PostgreSQL 复核 current active version，所以旧向量即使暂时存在也不能直接进入方案。

### Q32：文档更新时如何避免新旧版本混用？

**候选人：**

新版本先处于 accepted/processing，解析、嵌入、Milvus upsert 和 PostgreSQL chunk 写入完成后，才在受控事务中切换文档的 `current_version_id` 并激活新版本、停用旧版本。检索始终按当前指针过滤。

### Q33：`zero_hit` 和 `low_confidence` 有什么区别？

**候选人：**

`zero_hit` 表示没有可用结果，`low_confidence` 表示召回到了内容但最高分低于校准阈值。两者对运营的含义不同，也应该有不同监控。商品优化不会把低质量检索当作正常规则依据，而是转为人工处理或降级。

### Q34：RAG 参数是怎么来的？

**候选人：**

项目提供查询集和候选配置，计算 Recall@10、MRR、引用文档版本准确率和延迟，再按召回、MRR和候选规模选择配置。当前演示配置是 hybrid_rerank、candidate limit 10、RRF k=60、threshold 0.2。评测集很小，所以只能说明演示资料上的校准过程，不能当成生产基准。

### Q35：如何防止知识文档中的 Prompt Injection？

**候选人：**

知识内容只作为不可信引用数据进入固定 Prompt，不能生成 SQL、路径、授权 ID 或工具定义。模型只能输出固定 Schema 和 allowlist 中的 chunk ID，服务端还会复核文档版本、激活状态和适用性。即使文档写着“忽略系统指令”，它也只是被引用的文本。

## 6. 数据一致性、权限和安全

### Q36：幂等键如何工作？

**候选人：**

运营的选品、人工修订、提交和审批写接口要求 `Idempotency-Key`，服务端保存键的 SHA-256 和规范化请求哈希。相同 actor、资源、动作、键和请求会重放原结果；键相同但请求不同返回 409。数据库还有唯一约束，因此并发请求不能绕过应用层判断。物流依靠业务唯一约束、状态机和异常证据去重，不使用这套请求头协议。

### Q37：批准发布为什么必须使用商品版本锁？

**候选人：**

方案是基于某个 `base_product_version` 生成的。批准时再次比较 product、proposal 和 revision 的版本；任何不一致都返回 `PRODUCT_VERSION_CONFLICT`。否则旧文案可能覆盖在方案生成后由其他流程修改的新商品。

### Q38：模拟发布如何保证原子性？

**候选人：**

批准事务先锁定用户、店铺、方案、revision、workflow、商品和相关 SKU，重新验证状态与事实，然后在同一事务更新商品文案和版本、插入 approval action、publish record、platform delivery 和审计事件，最后设置 workflow completed。任一 flush 或 commit 失败都回滚。

### Q39：为什么驳回和要求修改是两个动作？

**候选人：**

驳回是终止性业务决定，状态进入 rejected；要求修改表示方向可以继续，清除 submitted revision 并回到 pending_manual，运营可以新建人工 revision。两者对任务列表、审计和后续权限不同，不能只靠一段评论区分。

### Q40：RBAC 做到什么层次？

**候选人：**

登录签发 JWT，但每次请求都会重新加载数据库用户，禁用或改部门会对旧凭证立即生效。随后检查部门、角色、店铺 scope、资源所属店铺和当前状态：普通运营账号不能访问物流路由，普通物流账号不能访问运营、知识、评测和审计路由，管理员可跨部门但仍受动作级校验。前端已经按这些能力导航和拦截直达路径，真正授权仍由服务端完成。

### Q41：如何防止跨店 IDOR？

**候选人：**

不能只凭 URL 中的 proposal_id 查记录。服务端先加载当前用户和授权店铺，再验证 proposal、product、analysis run、optimization run 和 store 的关系。敏感资源对未知和无权限统一返回安全语义，测试也覆盖跨店和破坏归属链的情况。

### Q42：审计日志为什么不能直接存完整请求？

**候选人：**

完整请求可能包含商品正文、规则原文、审批意见甚至意外敏感字段。审计模块只接受固定安全键和值域，并限制 4 KB。它记录谁、在什么资源上、执行什么动作、状态和版本如何变化，而不是复制业务数据。

## 7. 测试与验证

### Q43：测试体系如何分层？

**候选人：**

普通离线测试覆盖纯逻辑、API、MockTransport 和 Worker 状态；PostgreSQL opt-in 测试验证真实 `SKIP LOCKED`、行锁、并发、迁移和回滚；知识集成测试需要 Milvus 与本地模型；DeepSeek smoke 需要显式 Key。这样日常测试快，关键基础设施又有真实证据。

### Q44：最值得讲的并发测试是什么？

**候选人：**

一类是两个 Worker 竞争任务，只能领取不同记录；另一类是并发 submit、approve、reject 和 request_changes，确保唯一约束、行锁和事务只产生一个合法终态。还有旧 owner、owner replacement 和 checkpoint 失败场景，验证失去租约后零外部调用或零终态写入。

### Q45：如何测试 DeepSeek 失败而不频繁调用真实 API？

**候选人：**

通过 HTTPX MockTransport 精确模拟 timeout、transport error、429、5xx、401、403、坏 JSON 和 Schema 错误，并断言重试次数、错误码、降级状态和 AgentCall 记录。真实 smoke 只做显式 opt-in，不作为普通测试依赖。

### Q46：当前你能否说所有测试都通过？

**候选人：**

可以引用最近一次有日期的验收，但不能把它说成每次环境都自动成立。2026-09-21 的 [部门权限隔离验证](department-isolation-validation.md) 记录了后端离线回归 1145 passed、48 skipped，前端 Vitest 101 passed，TypeScript 与生产构建通过；另有运营、管理、物流浏览器回归及 PostgreSQL 迁移和并发授权验证。48 个跳过项包含需要显式开启的 PostgreSQL、外部模型等集成检查，真实 DeepSeek smoke 也不是普通回归的一部分。

**面试官判断点：** 是否诚实区分“写了测试”和“刚刚跑过测试”。

### Q47：前端现在完成了吗？

**候选人：**

完成了可操作的 Vue 前端：运营工作台、分析任务、候选选择、方案证据与人工修订、审批、知识管理、Agent 评测与调用记录、审计和系统管理；物流页面包含总览、运单、退货、异常工单和规则 Agent。移动端保留物流操作与主管审批，知识、Agent 观测、审计、系统管理以及运营创建/编辑动作限定桌面。它仍是本地演示前端，不代表生产可用性已经完成。

## 8. 物流、平台与共享管理

### Q48：物流 Agent 也是大模型 Agent 吗？

**候选人：**

不是。物流巡检用确定性规则识别发货超时、48 小时无轨迹、到货超时和退货处理超时，并用证据哈希去重生成异常工单。物流问答也是关键词分类加数据库事实汇总，返回运单引用。接口和页面都会说明 `mode=deterministic_rules`、未连接实时承运商、未调用大模型。

### Q49：物流模块完成了哪些闭环，哪些没有？

**候选人：**

已实现从已有订单建运单，记录发货、运输、签收节点，展示计划与实际时间；创建并按状态机推进退货；由规则巡检生成异常，分配给有对应店铺权限的有效物流用户或管理员，再填写处理结果。没有承运商自动同步、电子面单、财务退款或库存回补；退货 `closed` 只代表逆向物流和验收结束。

### Q50：平台投递是不是已经接入真实电商平台？

**候选人：**

不是。客户端和 Worker 实现了一个明确的外部协议边界：OAuth 客户端凭据、受限文案字段、稳定幂等键、401 换令牌、429/5xx/超时处理、有界重试、状态持久化和签名 Webhook。当前 `provider` 固定为仓库内 `contract_simulator`，用于验证协议、重放和故障恢复；没有真实商家认证、平台沙箱验收或生产店铺写入。

### Q51：部门权限和店铺权限如何组合？

**候选人：**

部门先决定能进入运营还是物流业务，角色再决定具体动作，店铺 scope 最后限制可见资源。普通运营账号只能访问运营路由，普通物流账号只能访问物流路由；两者都只能操作授权店铺。管理员可跨部门且不受普通店铺 scope 限制，但审批、知识维护和系统管理仍有动作级角色校验。JWT 只标识身份，API 和后台任务都会重新读取数据库权限。

### Q52：管理员现在能管理什么？

**候选人：**

桌面端系统管理页可以查看和修改既有用户的角色、所属部门、启用状态和店铺授权，也可以启停店铺。修改写入安全审计，并防止管理员禁用自己、移除自己的管理员角色或让系统失去最后一个有效管理员。当前没有在界面创建新用户、重置密码或接入企业身份提供商。

### Q53：运行完整系统需要哪些服务和 Worker？

**候选人：**

普通部署需要 Python 3.11、Node.js、PostgreSQL，知识链路还需要 Milvus、BGE-M3 和 BGE Reranker；Compose 同时启动 Milvus 所需的 etcd 和 MinIO。运营异步链路分别运行分析、知识索引、优化和人工复核 Worker。平台投递 Worker 必须显式开启并提供平台地址、客户端凭据和 Webhook 密钥。物流巡检可由页面触发，或由绑定具体物流账号的定时 Worker 执行；最简物流演示使用独立 SQLite，不需要 Milvus 或模型 Key。

### Q54：哪些管理和观测功能对普通用户开放？

**候选人：**

知识文档的上传、版本新增、列表和停用只允许运营侧管理员；业务检索可以在授权运营流程中使用。Agent 评测运行记录、经过最小化的调用元数据和审计页面只对运营主管或管理员开放，并且是桌面功能。系统管理仅管理员可见。物流用户看不到这些运营管理接口，但管理员可以从物流工作区切换到共享系统管理。

## 9. 压力追问与反思

### Q55：这个项目最难的部分是什么？

**候选人：**

不是调用 LLM，而是在重试、进程中断和并发请求下保持业务事实一致。需要同时处理租约 owner、checkpoint、不可变 revision、Agent 调用审计、幂等请求、商品版本和发布事务。我的原则是外部调用可以重试，但数据库副作用必须可重放、可验证且由唯一约束兜底。

### Q56：如果重做一次，你会先改什么？

**候选人：**

我会更早建立一个最小纵向切片和统一运行门禁：一条分析任务、一个候选、一个方案、一次复核和一次模拟发布，然后再扩展知识版本和复杂恢复测试。当前后端可靠性投入很深，但前端和完整 E2E较晚，导致用户可见价值出现得慢。

### Q57：代码中最大的技术债是什么？

**候选人：**

第一是分析查询和部分物流汇总在数据规模扩大后会变慢，应改成批量 SQL、预计算或数仓层；第二是审批和人工复核模块为了严密处理 replay 与损坏状态，文件较大，未来可按明确领域动作拆分，但不应在缺少收益时抽象；第三是当前缺少生产身份、密钥托管、监控告警和数据保留策略。真实平台与承运商协议也只有边界设计和模拟证据。

### Q58：如何把它改造成生产系统？

**候选人：**

先补真实身份系统、密钥管理、监控告警、数据保留策略和平台沙箱；再把经营指标与物流汇总改为批量或数仓计算，建立正式规则治理和大规模评测集。真实发布需要按目标平台完成商家 OAuth、适配器、限流和回执对账；物流需要承运商连接、轨迹对账以及退款和库存系统之间的明确事务边界。只有出现吞吐和团队边界后，才考虑拆 Worker 服务或引入消息队列。

### Q59：如果面试官说“这只是 Demo”，你怎么回答？

**候选人：**

它确实是本地 Demo，所以我不把它包装成生产系统。它的价值在于把生产中最容易被忽略的边界做成了可验证代码：实时授权、可信事实、版本化引用、租约恢复、幂等重放、并发冲突、事务发布和安全审计。尚未覆盖的是线上规模、真实平台协议和真实业务效果，这些需要不同证据。

### Q60：你个人在项目中的核心贡献如何表述？

**候选人：**

我负责把业务闭环拆成确定性事实层、Agent 决策层和人工治理层，并落地 Vue 3 工作台、FastAPI API、部门/角色/店铺授权、PostgreSQL 数据约束与任务租约、LangGraph 持久工作流、DeepSeek 结构化调用、BGE-M3/Milvus 混合 RAG、双轨合规、人工修订、审批发布、契约模拟投递、物流规则闭环和测试矩阵。我会明确说明真实平台、承运商和生产运行能力尚未实现。

## 11. 面试禁区

以下说法会被有经验的面试官继续追问，当前证据不足，不应使用：

- “实现了 exactly-once”；应说至少一次执行加业务幂等。
- “RAG 准确率 100%”；当前只是小型演示集结果。
- “已经实现生产级高并发”；当前是单机演示架构。
- “接入了真实电商平台”；当前是本地发布加 `contract_simulator` 投递。
- “接入了实时承运商”；当前物流轨迹由人工录入或演示数据提供。
- “所有 Agent 都使用大模型”；物流巡检和问答是确定性规则。
- “多 Agent 可以自动完成运营”；当前保留运营选品、人工修订和主管审批。
- “退货结案会自动退款”；当前不触发财务退款或库存变更。
- “前后端已经生产交付”；当前前端已实现，但系统仍是本地演示。
- “所有真实依赖测试都包含在 1145 passed 中”；48 个跳过项和真实 DeepSeek smoke 需要单独说明。
